## Architecture (4 layers)

1. **Research engine** — Claude Code (interactive in VS Code + headless `claude -p "$(cat prompts/...)"` spawned by the server). The ONLY layer that calls MCP tools. Writes structured JSON to disk.
2. **Data layer** — `data/accounts/{domain-slug}.json` (one per account, validated against `schema/account.schema.json`), `data/index.json` (search index), `data/meta.json` (refresh timestamps, run log, job queue state).
3. **Local server** — Express on 127.0.0.1: serves dashboard, `POST /api/refresh` ({query, mode: "light"|"deep"|"brief"|"activity"|"section"|"outreach", origin?: "user"|"auto", linkedin?: boolean}) spawns headless Claude, job queue (max 1 concurrent), chokidar → SSE push. No system crontab. **The nightly light cron and its hourly catch-up are DISABLED** (`refresh.nightly_light_enabled` / `refresh.catchup_enabled`, both false since 2026-09-03 — see "Spend discipline"); the code is intact behind those flags, and the catch-up now also gives up after 2 consecutive light failures instead of re-firing hourly forever. The book is re-synced by hand: `cd server && npm run refresh:book`. The morning Groove pull → draft batch is the one automatic job still running. Playwright is spawned available ONLY when mode=deep AND origin=user AND linkedin=true (the dashboard's "LinkedIn verify" checkbox); everything else gets `--disallowedTools 'mcp__playwright__*'`.
4. **Dashboard** — Vite + React + Tailwind SPA. Reads JSON + SSE. Never calls MCPs. Dark mode default, `/` focuses search. Styled with G2 "Elevate" design tokens (extracted from g2.com production CSS 2026-07-15) — see `@theme` in `dashboard/src/index.css`: brand red `#ff492c`, primary purple `#5746b2`, indigo-black dark surfaces, Figtree font. Rebuild (`npm run build` in `dashboard/`) after UI changes; the server serves `dist/`.

Build phases: 1) pipeline + one account end-to-end → 2) read-only dashboard → 3) server + auto-update → 4) scale to all accounts → 5) Playwright LinkedIn verification + messaging polish → 6) "Ask Claude" chat panel grounded on account JSON.

## Chat panel (Phase 6)

`POST /api/chat` ({slug, messages}) on the server calls the **Anthropic Messages API directly** (`@anthropic-ai/sdk`, `server/lib/chat.js`) — routed through G2's LiteLLM proxy (`config.chat.base_url` = `https://llmproxy.g2.com`, which passes the native `/v1/messages` surface straight through, streaming + prompt caching included; the Keychain key is a LiteLLM virtual key `sk-…`, ~25 chars, NOT an `sk-ant-` key). No MCPs, no tools; answers are grounded solely on the account's `data/accounts/{slug}.json`, which is passed as a cached system block. Streams NDJSON (`delta`/`done`/`error` lines) to the dashboard's `ChatPanel` (rendered in AccountDetail only when the server is up; plain-text replies by design). Model/max_tokens/history cap live in `config.chat` (currently `claude-sonnet-5`, adaptive thinking — see model policy below; `ai_visibility.model`/`community.model` are `null` and fall through to this same value, as does `draft.js`). **API key lives ONLY in the macOS Keychain** (service `bdr-dashboard-anthropic`, per `config.chat.keychain_service`) — never in a file or env var. Set/rotate: `security add-generic-password -a "$USER" -s bdr-dashboard-anthropic -w` (add `-U` to update). Missing key → clean 503 with that command; rejected key → server drops its cached client and re-reads the Keychain on the next request. The chat system prompt repeats the data-integrity caveats (unverified estimates, unconfirmed contacts, never cite G2 intent companies).

## AI-visibility module (7G-1)

`ai_visibility` dossier section = "does this company show up when a buyer asks an LLM for a shortlist in their category, and who gets cited?" — raw material for the AEO subject line. Runs **server-side** (`server/lib/aiVisibility.js`, reuses the chat client/LiteLLM proxy/Keychain key — no MCPs, not part of headless Claude's tool surface): 2-3 canned buyer-style completions (category shortlist from g2/firmographics categories → head-to-head vs a company the shortlist itself returned, never invented → "{name} reviews"), parsed for appearance/citations, ajv-validated atomic write, `refreshed_at` untouched. Trigger: `POST /api/ai-visibility/:slug` (dashboard "AI visibility" card ⟳) + auto-run after every successful deep refresh (`config.ai_visibility.run_after_deep`). Gotchas: generic company names ("You", "Button") only count as appeared via their domain — the prompt also uses the domain for those; `companies_returned` is a list-parse heuristic, `raw_excerpt` is ground truth. **Honesty rule: `company_appeared` is data, not copy** — if the company DOES appear, the angle flips to "who controls whether that continues"; never misrepresent the result. 6sense fields never feed these prompts.

## Community/UGC module (shipped 2026-07-30)

`community` dossier section = "where are this company's users talking in public, and is it real product feedback?" — raw material for the `ugc-narrative` play (users' public chatter is what LLMs learn from). ## Storyline layer (shipped 2026-08-23)

`data/accounts/<slug>.storyline.json` = the account-level narrative layer: ONE thesis (the `spine`) split into per-contact `cast` CHAPTERS, so five colleagues comparing inboxes find related angles that reinforce each other instead of five unrelated pitches. Optional and per-account — accounts without the file are completely unaffected. **Two ways a storyline gets created:** hand-authored via the `storyline-mesh` skill in an interactive session (the original, still-preferred path for judgment-heavy accounts), OR auto-generated by `server/lib/storylineBuilder.js` after a deep refresh (2026-09-01) — one direct LLM call (same client/no-MCP pattern as `ai_visibility.js`/`community.js`), gated by `config.storyline.auto_build_after_deep`/`auto_build_after_brief` (both `false` since 2026-09-13 — no unattended spend, see Spend discipline), firing only when the account has no storyline yet and >= `min_contacts_for_auto_build` `icp_contacts`. Both paths write the identical file shape and are governed identically by `data/plays/storyline.md`; the auto-builder NEVER overwrites an existing storyline (hand-authored or previously auto-built) and stamps `generated_by: "auto-storyline-builder"` + `reviewed: false` so the Storyline card can flag it — anything the builder isn't confident about lands in `verification[]` as `pending` rather than asserted, the same pre-send safety net a hand-authored file gets. Rules live in `data/plays/storyline.md` — a rules file like gates.md/anatomy.md, NOT a play (the draft engine reads the whole plays dir, so it is always in context). **Name the file by the RESEARCH-INDEX slug** (`cresta-com.storyline.json`, not `cresta.storyline.json`): resolution tries the account id directly, then falls back to matching the account NAME in `data/index.json`, so an index-slug name is the one that always resolves. `server/lib/storyline.js` owns that resolution and BOTH readers share it — `draft.js` imports `loadStoryline`, it must never carry its own copy, or the card and a draft could ground on different files. Draft side: injected as a cached system block after the dossier, plus one `userPayload` line making storyline.md binding for that draft. Read side: `GET /api/storyline/:accountId` (read-only; 404 when absent, a NAMED 500 when the hand-authored JSON has a syntax error so it can't be mistaken for "no storyline"; never reads outside `data/accounts`) feeds the **Storyline card** on the account detail view (`#/account/<slug>`, between "Community chatter" and "ICP contacts"): mode badge, spine, cast table with chapter + status chip, claims ledger, verification gate, and a pending-items banner leading the card. No editing UI by design.

- **Chapter discipline:** each contact's drafts use ONLY their assigned chapter's angle and facts. A fact reserved for another contact's chapter is off limits even when it would strengthen this draft — the mesh depends on each person holding a different piece.
- **E1→E2 handoff:** the first custom email withholds the chapter's specific (the names, the full list, the number behind the number) and asks whether they want it; the NEXT touch delivers it in full with no ask attached, whether or not they replied.
- **Claims ledger caps colleague references.** A draft may reference outreach to a colleague ONLY when `claims_ledger` has an entry for them, and the language is capped by that entry's `state` (`sent` → "I shared X with [name]"; `replied` → "trading notes"; `meeting` → "I'm talking with [name] on [day]"; `ae_thread_active` → "[AE] has been in an ongoing conversation with [name]", reserved for a live AE thread and confirmed with the AE first). Never invent a touch, never assert what a colleague thought or agreed to unless they wrote it. No qualifying entry = no colleague reference.
- **`pairings` decides who cites whom** so references form a mesh rather than everyone naming the same person. Use the pairing for the contact being drafted; never improvise a different one.
- **Verification gate:** `verification[]` items are pending/cleared/failed. Pending items render in `flag_warnings` (a pre-send check); a **failed item blocks drafting for that contact** until the storyline is updated. Currently the card enforces visibility but the draft engine still relies on the model copying pending items — moving that into code (and enforcing the failed-item block) is the open follow-up in PLAN-STORYLINE.md.
- **Modes:** `full_custom` = every email step is drafted, the storyline carries all five contacts. `template_flow` = Groove templates own their days and stats; the storyline fires only in the Day 8 free slot, VM scripts, and LinkedIn voice notes.
- **The storyline adds WHAT to say, never HOW.** gates.md and anatomy.md govern voice in full and nothing here overrides them — say-it-positive, no em-dashes in prospect-facing copy, self-intro at the back on first-ever touches, C-suite gets ownership-routing questions only, ≤100 words.

## Cowork / desktop sessions are repo-first (Declan's ruling, 2026-08-25)

This repo IS the living database — every session that researches accounts or drafts outreach reads from it and writes back to it. Ruling exists because a 2026-08-25 morning Cowork session re-researched four accounts from scratch, produced thinner storylines than the overnight run already sitting in `data/accounts/`, drafted against stale July windows, and left everything stranded in session outputs. Rules:

1. **Connect this folder first** (`~/Desktop/bdr-dashboard`) in any Cowork session doing account work. No connection → no account work; ask for it.
2. **Read before researching.** For each account on the work order, check `data/accounts/<slug>.storyline.json`, `data/accounts/<slug>.json`, and the newest `data/drafts/research-*/<slug>.md` BEFORE any MCP call. Research only fills gaps; a re-pull of something already dated this week is wasted credits and drift risk.
3. **Write deltas, never parallels.** New verified facts merge into the existing storyline file (bump `updated`, extend `verification`/`facts`/`cast` in place). Never write a second storyline for the same account anywhere else, and never leave account intel only in session outputs. Firsthand identity/email corrections ALSO go to "Known account corrections" below — that list is the cross-session memory that survives storyline rewrites.
4. **Sends docs land in `data/drafts/`** (`storyline-sends-<date>.md` or the due-day file), holds and verification queues included, so the next session — or the overnight run — inherits them.
5. **Storyline JSONs must stay `jq`-parseable** (the server 500s loudly on syntax errors by design). Validate after editing.
6. **Session outputs folder is scratch only.** If it produced something worth keeping, it gets merged here before the session ends.

## Data-integrity rules (non-negotiable)

1. **Domain beats name.** Resolve canonical domain first; every enrichment call keys off it.
2. **ZoomInfo sequence:** `search_companies` with `companyWebsite` (free) → `account_research` with returned `zoominfoCompanyId` (paid). Never paid calls off a name match.
3. **Never report headcount/revenue from a single enrichment source.** ZoomInfo is frequently stale ~an order of magnitude for private companies. Cross-check LinkedIn company page (Playwright) or careers-page role count. Unverifiable → flag `unverified_estimate`, UI renders warning badge.

## LinkedIn / Playwright constraints

Verification tool, NOT a scraper: low-volume targeted lookups (confirm one contact's title/tenure, read company headcount), deep refreshes only, human-like pacing. Automated LinkedIn access carries account-restriction risk — volume stays deliberately low. Lookup fails → mark contact `unconfirmed`, never block the pipeline.

**Phase 5 auth approach (implemented 2026-07-15): NO scripted logins, NO stored credentials.**
- Never store LinkedIn (or Sales Nav) username/password anywhere — not in the repo, not gitignored files. Scripted headless logins also trip LinkedIn's automation defenses (checkpoints/CAPTCHAs) and are a restriction signal.
- **Chrome 136+ refuses automation on the default user data dir**, so the original "ride Declan's existing profile" plan is impossible. Instead: a **dedicated persistent Chrome profile** at `~/Library/Application Support/bdr-dashboard/chrome-profile` (outside the repo; `config.linkedin.profile_dir`). Declan logs into LinkedIn + Sales Nav there once, by hand, **inside a Playwright-launched Chrome** (`cd server && npm run linkedin:login`); the Playwright MCP is registered with `--browser chrome --user-data-dir <that dir>` and inherits the session. Real Chrome never needs to be closed.
- **The profile must ONLY ever be opened through Playwright** (`npm run linkedin:login` / `linkedin:check` / the MCP). Playwright launches Chrome with `--use-mock-keychain`; a normally-launched Chrome (`open -na …`) uses the real Keychain, can't decrypt the Playwright-written cookies, and **silently destroys them** (and vice versa — verified the hard way 2026-07-15, first login was lost this way).
- Session expired (authwall in a run)? `cd server && npm run linkedin:login`, log in by hand, **Cmd+Q** the window (closing it isn't enough — the process holds the profile lock), then `npm run linkedin:check` to confirm (exit 0 = logged in).
- Runtime gating: Playwright only for deep + `origin: "user"` + `linkedin: true` jobs (server hard-block otherwise; the dashboard exposes this as an opt-in "LinkedIn verify" checkbox, default OFF). LinkedIn volume stays a deliberate per-run choice — check the box only for accounts you're about to call, not for every daily pick. Per-run budgets in `config.linkedin` (`max_contact_lookups_per_run`, `max_page_loads_per_run`, `min_seconds_between_pages`). Procedure lives in `prompts/refresh-account.md` Step 9b. Authwall/checkpoint mid-run → stop ALL LinkedIn use for that run, mark `attempted_failed`, never retry or attempt login.
- Sales Nav lookups ride the same session, same rules: targeted verification of specific contacts only, never bulk.
- If any future integration genuinely needs a stored secret → macOS Keychain, never a file.
- ZoomInfo `enrich_contacts` remains the first verification line; LinkedIn is the upgrade path for contacts ZI can't confirm.

## Groove CLI / Playwright constraints

Deliberate, explicit override (confirmed 2026-08-10) of the prior "never attempt a Groove integration" rule — Groove has no official/public API, so `server/lib/groove.js` calls its own internal REST API directly, reverse-engineered by watching real network traffic. This is a completely separate, opt-in channel from the existing one-tap dashboard logging and the SF-Task-derived `data/outreach.json` mirror — neither of those changed.

- **Separate dedicated Chrome profile** at `~/Library/Application Support/bdr-dashboard/groove-chrome-profile` (`config.groove.profile_dir`) — never shared with the LinkedIn profile, so a problem with one (corruption, session loss, restriction risk) never touches the other. Same rule as LinkedIn: **the profile must ONLY ever be opened through Playwright** (`npm run groove:login` / `groove:check` / `groove:capture` / the CLI's internal session harvest) — Playwright's `--use-mock-keychain` means a normally-launched Chrome on this profile silently destroys its cookies, exactly as documented above for LinkedIn.
- Login: `cd server && npm run groove:login`, log in by hand, **Cmd+Q** the window (closing it isn't enough — the process holds the profile lock). Check: `npm run groove:check` (exit 0 = logged in, 1 = authwall, 2 = error). No credentials are ever stored — same as LinkedIn.
- **Endpoint discovery is a required, hand-curated step, not automated.** `npm run groove:capture` passively records real Groove network traffic while a human exercises each target action; the raw capture must be manually reviewed into `data/groove/endpoint-map.json` before `lib/groove.js` can use it. Never hand-guess a Groove endpoint path. **If Groove ever changes its UI and a call starts failing or returning an unexpected shape, re-run the capture — don't patch around it.**
- **Fail loud, never silently retry.** Any non-2xx response, unexpected response shape, or HTML/login page instead of JSON throws immediately naming what mismatched. Unlike a failed LinkedIn lookup (which just marks a contact `unconfirmed` and moves on), a Groove write is consequential state in a live flow — a retried call against a since-broken endpoint could double-log a call or mis-advance a real step.
- **Rate limits in `config.groove` (`max_writes_per_run`, `max_writes_per_day`, `min_seconds_between_writes`) are UNVERIFIED PLACEHOLDERS** — unlike LinkedIn, this project has no prior experience with Groove's bot-detection posture. Tighten immediately on any 429/CAPTCHA/lockout signal and treat any such signal as a hard stop, never a retry.
- Every write subcommand supports `--dry-run` — use it before any bulk action or after touching the endpoint map.
- **WRITES are human-invoked only; READS may run unattended (Declan's ruling, 2026-08-25 — narrows the original blanket rule).** Every Groove *write* (`log-call`, `log-email`, `advance-step`, `enroll`, `remove`) stays a hand-typed terminal command: a write is consequential state in a live flow, the rate limits in `config.groove` are still unverified placeholders, and a retried call against a since-broken endpoint could double-log a call or mis-advance a real step. Groove *reads* (`due-list`, `flows-list`, `steps-list`, `contact-show`) carry none of that — three GETs per flow, nothing counted against the write limits — so they may run on a schedule. The Groove CLI still must never be added to `.claude/settings.json`'s headless allowlist or reachable from any `claude -p` pipeline run; the morning job is plain node, no headless Claude. `groove:login` remains hand-only, like `linkedin:login`.
- **Morning pull → drafts (`server/lib/morningPull.js`, shipped 2026-08-25).** Config in `config.groove.morning`: cron `0 7 * * 1-5`, plus boot + hourly catch-up so a laptop that was asleep at 7am still gets its drafts when the lid opens; idempotent per calendar day, and gated to `earliest_hour`–`latest_hour` so a 3am boot never generates Groove traffic. Chain: `groove-due-pull.js --flow <id>` per configured flow → one merged CSV (merged so `draft.js`'s per-account `batchContext` anti-duplicate-opener guard sees the whole day) → `startDueBatch()`. `flows: [1483166]` = "BDR 2 FY27"; `1571660` = "Claude Agent Flow Calls + Linkedin". `GET/POST /api/morning` for status and a manual `force` kick. **Fail loud, draft nothing:** a dead session or a changed Groove shape stops the run with the error recorded — it must NEVER fall back to the SF mirror's `flow_day`, which is a stale snapshot (see the never-infer-groove-steps rule). A wrong step drafts the wrong message into a live flow, which is worse than no draft.
- **`harvestSession()` probes `/api/v2/user` before caching cookies.** The URL-regex check alone is not enough — Groove serves its login page from the host root with no path marker, so a dead session sails past it and the harvest caches cookies that 401 on the first real call (seen 2026-08-25: harvest "succeeded", `flows-list` returned an opaque `NotAuthenticatedError`). `groove-session-check.js` learned this on 2026-08-18; the same probe now guards the path every unattended run takes.
- `data/groove/` (endpoint map, session cache, write-log) stays gitignored under the existing `data/*` rule — never add an exception for it.

## Email voice rules (2026-08-12)

`data/plays/gates.md` (from the Aug 2026 CXO Engagement Workshop, PDF in `data/`) governs voice/framing for ALL drafted outreach — server draft engine, play hooks, and in-session drafting (`/draft-email` skill). Core: the reader's six mental gates; we-we rule (≤2 self-references per body — G2 facts about THEM are fine, G2-as-us is banned from the body); preview text about them; problem-prompter first-touch shape; seek-to-be-corrected tonality; **say it positive** (2026-08-17 — both litotes, "not uncommon"/"no small feat", AND contrastive negation, "it's not X, it's Y"/"not just X, but Y", are banned in body copy on every channel; write the positive half alone. Genuine hypotheses "not sure if X…" and true negative facts stay); **abstraction as actor** (2026-08-26 — a body sentence whose subject is an abstract noun *doing* something is banned: "that's the language forming your category story before your team gets a say in it". The reduced-relative grammar is innocent, the nouns are the problem. Pointable test: can the reader point at the sentence's subject? A page, a review count, a date, a job posting, a competitor, a person — keep. "The language"/"the story"/"the signal"/"the conversation"/"the narrative"/"the shift" acting on another abstraction — name who actually acts, or cut. Reduced relatives on concrete nouns and companies-as-agents stay). Every draft carries a self-scorecard (`{self_refs, failed_gates, time_ask}`), rendered as chips on Due/Accounts draft cards. anatomy.md's explicit templates win where they overlap. Applies to every persona, not just CXO.
